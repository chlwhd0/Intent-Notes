## 이 문서의 읽는 법

1차 개선 PRD와 같은 방식으로, 문제에서 해결방안까지 **한 줄기로** 이어지도록 구성했습니다.

| 단계 | 개수 | ID 예시 | 위치 |
|---|---|---|---|
| 문제 정의 | 10개 | `APRB-01` ~ `APRB-10` | 3.1 |
| 최종 문제 | 4개 | `AFP1` ~ `AFP4` | 3.3 |
| 가설·지표 | 10개 | `AFP1-H1` ~ `AFP4-H2` | 4 |
| 해결방안 | 15개 | `AFP1-H1-S1.fill*meta` ~ `AFP4-H2-S2.privacy` | 5.1 |
| 기능 요구사항 | 15개 | `AFR-01` ~ `AFR-15` | 6 |

**ID 앞의 `A`는 이 문서가 AI 기능편이라는 표시입니다.** 1차 개선 PRD도 `FP1`, `FR-01` 같은 ID를 쓰기 때문에, 두 문서의 번호가 섞이지 않도록 이 문서의 ID에는 `A`를 붙였습니다(`AFP1`은 이 문서의 최종 문제 1번, `FP1`은 1차 개선 PRD의 최종 문제 1번).

**ID에는 부모가 들어 있습니다.** ID만 봐도 어느 문제와 가설에서 나온 것인지 보입니다.

| ID 형식 | 뜻 | 읽는 방법 |
|---|---|---|
| `AFP2` | 최종 문제 2번 (AI Final Problem) | 공개 전 안전 문제 |
| `AFP2-H1` | AFP2의 첫 번째 가설 (Hypothesis) | 앞마디 `AFP2` = 부모 최종 문제 |
| `AFP2-H1-S1.rule*check` | AFP2-H1의 첫 번째 해결방안 (Solution). 점 뒤는 내용 키워드, 여러 단어는 `*`로 연결 | 앞 두 마디 `AFP2-H1` = 부모 가설, 키워드 `rule*check` = 규칙으로 점검 |
| `AFP1-H3-S1.pdf*sum` | AFP1-H3의 첫 번째 해결방안. `pdf*sum` = PDF 첨부 파일 요약. **기능은 삭제했고 이름만 남김** | ID만 봐도 출처와 내용이 보임 |
| `AFR-03` | 기능 요구사항 번호 (개발 단위) | 해결방안이 구현되는 기능 |

### 1.2 처음 계획에 없던 추가 (사용자 요청)

AI 기능과 함께 쓰다가 생긴 요청으로 추가한 것입니다. 기능 번호(`AFR`)는 따로 붙이지 않았습니다.

| 묶음 | 내용 | 확인 |
|---|---|---|
| 썸네일 "없음" | 글쓰기에서 기본 모양 6개 외에 **"없음"**을 고를 수 있다(저장 값 -1, 보안 규칙도 -1~5 허용). 없음이면 썸네일 칸 자체를 두지 않고 투명하게 둔다. 글 목록, 첫 화면 목록, 글 상세, 글 관리 목록, 관리자 화면에 같은 규칙을 쓴다 | 구현·배포, 화면에서 확인 |
| 모바일 관리자 메뉴 | 위 메뉴(ALL POSTS 등)는 한 줄로 두고 박스를 없앴다. **ADMIN은 눌러야 하위 메뉴(MANAGE MENUS·MANAGE POSTS·RETRO SUMMARY·AI USAGE)가 펼쳐지고**, 펼치고 접을 때 짧은 애니메이션이 나온다(모션 줄이기 설정이면 즉시). NEW POST는 브랜드 이름 줄 오른쪽에 둔다. 관리자 제목줄의 "새 글 쓰기" 버튼은 삭제했다. 컴퓨터 화면은 하위 메뉴가 항상 보인다 | 구현·배포, 모바일 폭(375px)에서 확인 |
| 모바일 관리자 화면 크기 정돈 | 메뉴 관리(이름 입력칸과 ↑ ↓ 삭제를 한 줄에, 둘째 줄에 나만 보기 설정과 글 개수), 글 관리 표, 글 목록 행, 글쓰기 입력칸(글자 12px), 회고 정리, AI 이용 현황 표의 글자·버튼 크기와 배치를 위쪽 메뉴에 맞춰 줄였다 | 구현·배포, 모바일 폭에서 확인 |
| 창이 작은 컴퓨터 화면 | 창을 줄여도 배치를 바꾸지 않고 옆으로 밀어 볼 수 있게 했다 | 구현·배포 |
| 모바일 AI 도우미 창 | 글쓰기에서 AI 도우미를 쓰면 화면이 너무 길어져서, 오른쪽 아래 **AI 버튼**(확인할 것 개수 표시)을 누르면 **아래에서 올라오는 창**으로 쓴다. 발행이 막히면 자동으로 열린다 | 구현·배포, 모바일 폭에서 확인 |
| 회고 초안 전달 | 회고 정리에서 만든 제목·요약도 글쓰기로 함께 보낸다(전에는 본문만 넘어왔다) | 구현·배포 |
| 오류 수정 | 모바일에서 글쓰기의 [취소]·[발행하기]가 숨던 문제를 고쳤다 | 구현·배포 |

## 2. 개요

**배경.** 블로그는 글쓰기, 방문자 로그인과 댓글, 조회수, 공유하기, 이미지·파일 첨부를 갖췄고, 1차 개선 PRD에서 측정 체계(GA4 이벤트, 대시보드)를 설계했습니다. 이 문서는 시선을 한 단계 앞으로 옮겨, **글 한 편이 만들어져서 공개되고 읽히기까지의 반복 작업과 실수 위험**을 봅니다.

**문제.** 2026-11-24에 공개 사이트를 확인하니, 공개 글 4개 중 **2개가 한 줄 요약이 비어 있고**, 4개 모두 **본문이 50자 이하**이며(5·10·23·36자), 그중 2개는 내용이 PDF 첨부에만 있습니다. 푸터에는 **채우지 않은 칸 `[이름]`이 그대로 공개**되어 있습니다. 공개 전 확인(실명, 내부 자료, 정확한 수치, 채우지 않은 칸)은 개발 지침 문서의 규칙으로만 있고, 사람이 눈으로 확인합니다. 회고(나만 보기)는 쌓여도 공개 글로 바뀌지 못합니다.

**솔루션.**

1. 글을 쓸 때 AI가 한 줄 요약·검색용 설명·제목 후보를 **제안**하고, 회고 정리로 글 쓰는 부담을 줄입니다.
2. 공개 전에 규칙과 AI로 **채우지 않은 칸·전화번호·정확한 수치·실명 추정·내부 자료**를 점검하고, 해결하기 전에는 발행하지 못하게 합니다.
3. 방문자 화면에는 미리 만들어 저장해 둔 **3줄 요약**과 글자 유사도로 계산한 **관련 글**을 보여 줍니다.
4. 모든 AI 결과는 **"AI 초안" 표시 + 내가 [적용]해야 반영**되게 하고, 호출 횟수·개인정보를 통제합니다.

### 2.1 블로그 기획 PRD·1차 개선 PRD와의 연결

| 이전 문서에서 | 이 문서에서 이어지는 곳 |
|---|---|
| 블로그 기획 PRD 필수 요구사항 3: 회고는 나만 볼 수 있고 나만 쓸 수 있다 (`CLAUDE.md`) | 회고 정리(`AFP1-H4`)는 초안도 처음에는 나만 보기로 저장하고, 원문을 외부 AI로 보내지 않는 선택지를 둔다 |
| 개발 지침의 주의사항: 회사 내부 자료·고객 정보·실명·정확한 수치·`[이름]`·`[샘플]`은 공개 전에 직접 확인 | 발행 전 점검(`AFP2`)이 이 규칙을 화면의 점검으로 옮김 |
| 블로그 기획 PRD 필수 요구사항 14: 글에 파일을 첨부(PDF 등, 25MB 이하) | 첨부 요약(`AFP1-H3`)은 삭제함. 첨부는 그대로 |

| 1차 개선 PRD `FR-13`: 처리방침 갱신 | `AFR-15`: 외부 AI 서비스 사용 안내를 처리방침에 추가 |
| 블로그 기획 PRD 13장 비기능 요구사항: 보안·개인정보 | 7장과 `AFR-12`~`AFR-15` |

## 3. 문제

### 3.1 문제 발굴

**사용자**가 겪는 **문제**와 그 **해결 방안**을 먼저 정리했습니다. 처음 발굴한 문제 10개이며, 3.3에서 4개의 최종 문제로 묶습니다. 문제마다 확인한 사실(근거)은 [3.2.1](#321-점검-결과-및-인사이트)에 모아 두었습니다.

| ID | 사용자 | 문제 (사용자가 겪는 일) | 해결 방안 |
|---|---|---|---|
| `APRB-01` | 운영자 | 글을 올릴 때마다 한 줄 요약과 검색용 설명을 손으로 써야 해서, 비어 있거나 부실한 글이 생긴다 | 본문을 읽고 요약·설명을 제안하는 글쓰기 보조 |
| `APRB-02` | 운영자 | 제목을 정하는 데 시간이 걸리고, 내용을 담지 못한 제목이 되기 쉽다 | 제목 후보 3개 제안 |
| `APRB-03` | 운영자 | 공개 전 확인을 눈으로만 해서 `[이름]` 같은 채우지 않은 칸이 공개 화면에 남는다 | 저장 직전 자동 점검, 해결하기 전에는 발행 막기 |
| `APRB-04` | 운영자 | 실명·내부 자료·정확한 수치·전화번호가 섞여도 스스로 알아채기 어렵다 | 규칙 점검 + AI 문맥 점검 |
| `APRB-05` | 운영자, 방문자 | 글의 내용이 첨부 PDF에만 있어서, 운영자는 본문에 옮겨 쓰기 번거롭고 방문자는 파일을 열어 보기 전에 무슨 내용인지 알 수 없다 | 첨부 PDF의 핵심 3줄 요약을 본문에 넣기 (**해결하지 않음**: 첨부 요약 기능 삭제) |
| `APRB-06` | 운영자 | 회고가 쌓여도 나만 보기라서, 반복되는 배움을 공개 글로 만들려면 처음부터 다시 읽고 써야 한다 | 회고 정리: 반복되는 배움 찾기 → 공개 글 초안(처음에는 나만 보기) |
| `APRB-07` | 방문자 | 긴 글의 핵심을 읽기 전에 알기 어렵다 (짧은 시간에 훑어보는 채용 담당자) | 글 위쪽의 3줄 요약 |
| `APRB-08` | 방문자 | 글을 다 읽고 나서 이어서 볼 글을 스스로 찾아야 한다 | 내용이 비슷한 글 추천 |
| `APRB-09` | 운영자, 방문자 | AI가 만든 내용이 틀려도 걸러지지 않고 사람이 쓴 것과 구분되지 않으면, 공개 글의 신뢰를 잃는다 | "AI 초안" 표시, 내가 [적용]해야 반영, 이용 기록 |
| `APRB-10` | 운영자 | AI 호출 비용과 원문(본문·텍스트 파일·회고)의 외부 전송을 통제하지 못할 수 있다 | 방문자 열람 때 호출 없음, 월 한도, 외부 전송 최소화, 처리방침 갱신 |

**사용자별로 보면**

| 사용자 | 문제 개수 | 문제 |
|---|---|---|
| 운영자 (글을 쓰고 공개하는 사람) | 8개 | `APRB-01` `APRB-02` `APRB-03` `APRB-04` `APRB-05` `APRB-06` `APRB-09` `APRB-10` |
| 방문자 (글을 읽는 사람) | 4개 | `APRB-05` `APRB-07` `APRB-08` `APRB-09` |

운영자 문제가 대부분이라 이번 개선은 **운영자 쪽을 먼저** 만들고, 방문자 쪽(`APRB-07`, `APRB-08`)은 만든 뒤 효과를 지표로 확인합니다.

### 3.2 문제 검증

설문 대신, 공개 사이트와 코드에서 **지금 확인할 수 있는 사실**로 검증했습니다(2026-11-24 공개 글 4개의 페이지 확인, 푸터 확인, 빌드 코드의 점검 항목 확인). 관리자 로그인이 필요한 화면(회고 글 수 등)은 직접 보지 못했습니다.

#### 3.2.1 점검 결과 및 인사이트

| # | 확인한 것 | 현재 상태 | 근거 | 연결 문제 |
|---|---|---|---|---|
| 1 | 공개 글의 한 줄 요약 | **4개 중 2개가 비어 있음 (50%)** | 글 페이지의 요약 자리가 비어 있음 | `APRB-01` |
| 2 | 공개 글의 본문 길이 | **4개 모두 50자 이하** (5·10·23·36자) | 글 페이지 본문 | `APRB-05` `APRB-07` |
| 3 | 첨부 파일이 있는 글 | 2개 (각 1개). 둘 다 요약이 비어 있고 본문이 짧음 | 글 페이지의 첨부 파일 영역 | `APRB-05` |
| 4 | 공개 화면에 남은 채우지 않은 칸 | **`[이름]`이 푸터에 그대로 보임** | 홈 화면 푸터 | `APRB-03` |
| 5 | 공개 전 점검 장치 | 빌드 때 설정·글 제목의 채우지 않은 칸만 경고. 본문·개인정보·내부 자료 점검은 없음 | 빌드 코드의 점검 항목 | `APRB-03` `APRB-04` |
| 6 | 제목·설명 작성 지원 | 없음 | 글쓰기 화면 | `APRB-02` |
| 7 | 회고를 공개 글로 바꾸는 지원 | 없음. 회고는 나만 보기 | 개발 지침 필수 요구사항 3 | `APRB-06` |
| 8 | 이어 읽기 | 같은 메뉴의 이전·다음 링크만 | 글 상세 화면 | `APRB-08` |
| 9 | AI 결과의 표시·검수 규칙 | 아직 없음 (새 기능이라 설계가 필요) | - | `APRB-09` `APRB-10` |

**인사이트:** 눈으로 바로 확인되는 문제는 세 가지입니다. ① 요약 공백 50%, ② 본문이 거의 없고 내용이 PDF에 있음, ③ 채우지 않은 칸이 공개 화면에 남음. 이 셋은 AI가 없어도 "있어야 할 점검이 없다"는 뜻이라 우선순위가 높습니다. 반면 방문자 쪽 문제(`APRB-07`, `APRB-08`)는 증거가 약해서, 만든 뒤 1차 개선의 이벤트로 효과를 확인하는 가설로 둡니다.

### 3.3 문제 최종 정의

#### 3.3.1 우선순위 결정 (RICE + MoSCoW)

RICE = Reach(영향 범위, 10점 만점) × Impact(영향도, 0.25~3) × Confidence(확신도) ÷ Effort(공수, 인일). 모든 수치는 기획자 추정치이며 사용 데이터가 쌓이면 보정합니다.

| 과제 | 최종 문제 | R | I | C | E | RICE | MoSCoW |
|---|---|---|---|---|---|---|---|
| `APRB-09`·`APRB-10` AI 초안 표시·승인, 이용 기록, 호출 한도, 처리방침 | `AFP4` | 10 | 3 | 90% | 2 | 13.5 | Must |
| `APRB-03`·`APRB-04` 규칙 점검 + 발행 막기 | `AFP2` | 10 | 2 | 90% | 1.5 | 12.0 | Must |
| `APRB-01`·`APRB-02` 글쓰기 보조 (요약·설명·제목) | `AFP1` | 8 | 2 | 80% | 2 | 6.4 | Should |
| `APRB-04` AI 문맥 점검 (실명 추정, 내부 자료) | `AFP2` | 6 | 2 | 50% | 2 | 3.0 | Should |
| `APRB-07` 3줄 요약 | `AFP3` | 7 | 1 | 60% | 2.5 | 1.7 | Should |
| `APRB-05` 첨부 파일 요약 | `AFP1` | 3 | 1 | 70% | 2 | 1.1 | Could (해결하지 않음) |
| `APRB-06` 회고 정리 | `AFP1` | 2 | 2 | 50% | 3 | 0.7 | Could |
| `APRB-08` 관련 글 추천 | `AFP3` | 4 | 1 | 40% | 3 | 0.5 | Could |
| 방문자 질문 답변(챗봇), 영어 번역, 댓글 자동 분류·답글 | - | 3 | 1 | 40% | 4 | 0.3 | Won't |

`APRB-09`·`APRB-10`(AI 초안 표시·승인, 한도, 처리방침)은 점수가 가장 높지만 사실은 **다른 모든 AI 기능의 전제 조건**이라 가장 먼저 만듭니다. 규칙 점검은 AI 없이도 만들 수 있어 둘째입니다. Won't 항목은 이번 범위에서 제외하며 사유는 6.6에 적었습니다.

#### 3.3.2 문제 최종 정의

처음 발굴한 문제 10개를 **4개의 최종 문제**로 묶었습니다.

| 최종 문제 | 한 문장 정의 | 묶인 문제 (처음 10개 중) | 선정 이유 |
|---|---|---|---|
| `AFP1` **작성 부담** | 글을 올릴 때마다 요약·설명·제목을 손으로 쓰고, 내용이 PDF나 회고에 있어 글로 옮기기 번거롭다 | `APRB-01` `APRB-02` `APRB-05` `APRB-06` | 가장 자주 반복되는 일이고, 요약 공백 50%가 눈에 보인다 |
| `AFP2` **공개 전 안전** | 공개 전에 실명·내부 자료·수치·채우지 않은 칸을 사람의 눈으로만 확인한다 | `APRB-03` `APRB-04` | 공개된 뒤에는 되돌리기 어렵고, 이미 채우지 않은 칸이 공개되어 있다 |
| `AFP3` **독자 이해·이어 읽기** | 방문자가 글의 핵심을 빨리 알고 이어서 볼 글을 찾기 어렵다 | `APRB-07` `APRB-08` | 방문자 경험을 개선하는 유일한 축이지만 증거가 약해 측정으로 확인이 필요하다 |
| `AFP4` **AI 신뢰·통제** | AI 결과가 틀려도 걸러지지 않고, 비용과 원문의 외부 전송이 통제되지 않을 수 있다 | `APRB-09` `APRB-10` | 모든 AI 기능의 전제. 늦게 설계하면 기능마다 다시 고쳐야 한다 |

**핵심 문제:** 글을 쓰고 공개하는 반복 작업과 공개 전 실수 위험을 사람이 혼자 감당하고 있어, 이것을 **"AI는 제안만 하고 사람이 확인하는" 방식**으로 덜어 주되 신뢰·비용·개인정보를 통제해야 한다.

**이번에 제외한 것:** 댓글 관리(스팸 분류·답글 초안), 방문자 질문 답변(블로그 챗봇), 영어 번역. 댓글과 방문자 질문은 방문자가 쓴 글을 외부 AI로 보내는 일이라 개인정보·악용·비용 통제가 먼저 필요합니다.

최종 문제마다 가설을 세우고, 가설마다 확인할 지표를 정했습니다. 가설 ID는 부모 최종 문제를 앞에 붙였습니다. 효과는 1차 개선 PRD에서 설계한 이벤트(`post_read`, `attachment_download`, `select_content`)와 관리자 이용 기록(6.2)으로 확인합니다.

| 최종 문제 | 가설 ID | 가설 | 지표 | 측정 방법 |
|---|---|---|---|---|
| `AFP1` 작성 부담 | `AFP1-H1` | 글쓰기 보조가 있으면 요약·설명이 채워진 글 비율이 오르고 글 한 편을 올리는 시간이 줄어든다 | 요약·설명이 채워진 공개 글 비율 (현재 요약 50%)<br>제안 적용률 = 적용한 제안 ÷ 만든 제안<br>글 작성 시작~발행 시간 | 관리자 이용 기록, 글 데이터 |

| | `AFP1-H3` | (삭제됨) 첨부 파일 요약이 파일 옆에 붙은 글은 읽기율과 첨부 내려받기가 늘어난다 | 요약이 있는 글 vs 없는 글의 읽기율(`post_read`), 내려받기 수(`attachment_download`) | GA 이벤트(1차 개선), 관리자 이용 기록 |

| | `AFP3-H2` | 관련 글 추천이 같은 메뉴의 이전·다음보다 추가 글 열람을 만든다 | 추천 위치 선택률 = `select_content`(`location=related`) ÷ 글 조회, 방문당 글 수 | GA 이벤트(1차 개선 `FR-07` 확장) |

| | `AFP4-H2` | 방문자 열람 때는 호출하지 않고 월 한도를 두면 비용이 한도 안에서 운영된다 | 월 AI 호출 수·비용, 방문자 열람당 AI 호출 수(목표 0) | 서버 함수 기록, AI 제공자 사용량 |

**효과 판단 기준 (v1 가설):** 글이 4개뿐이라 방문자 지표는 몇 달 동안 표본이 작습니다. 그래서 운영자 쪽 지표(요약 채움률, 위반 0건, 적용률)를 **먼저 판단 기준**으로 삼고, 방문자 지표(읽기율, 추천 선택률)는 1차 개선의 기준(조회 50 이상 글)을 넘은 글에만 적용합니다.

## 5. 해결방안

### 5.1 솔루션 정의

**목표 문장:** "블로그 운영자가 글을 쓰고 공개하는 반복 작업과 공개 전 확인을 AI의 제안으로 덜고, 방문자는 글의 핵심과 이어 읽을 글을 바로 볼 수 있게 한다. 단, AI는 제안만 하고 공개되는 것은 내가 확인한 것뿐이다."

해결방안 ID에는 부모 가설이 들어 있습니다. 예를 들어 `AFP2-H1-S1.rule*check`는 `AFP2`(공개 전 안전)의 `AFP2-H1`(규칙 점검 가설)에서 나온 첫 번째 해결방안입니다.

#### 최종 문제 AFP1. 작성 부담

> 글을 올릴 때마다 요약·설명·제목을 손으로 쓰고, 내용이 PDF나 회고에 있어 글로 옮기기 번거롭다.

| 해결방안 ID | 출발 가설 | 해결 방안 | 완료 기준 | 기능 | 우선 |
|---|---|---|---|---|---|
| `AFP1-H1-S1.fill*meta` | `AFP1-H1` 글쓰기 보조로 요약·설명이 채워진다 | 본문을 읽고 한 줄 요약(명사형)을 제안. 마음에 드는 것만 [적용]. 검색용 설명은 한 줄 요약에 합침 | 적용하기 전에는 입력칸이 바뀌지 않는다. 적용 후에도 직접 고칠 수 있다 | `AFR-01` | P1 |
| `AFP1-H2-S1.title` | `AFP1-H2` 제목 후보는 참고용으로 쓰인다 | 제목 후보 3개 제안, 하나를 골라 [적용] | 후보를 눌러야만 제목이 바뀌고, 기존 제목은 그대로 둘 수 있다 | `AFR-02` | P1 |
| `AFP1-H3-S1.pdf*sum` | `AFP1-H3` 첨부 파일 요약을 넣으면 읽기와 내려받기가 늘어난다. **(삭제됨. ID의 `pdf`는 처음 이름이고 기능은 만들었다가 지움)** | 첨부 파일 요약 | 해당 없음 | `AFR-03`(삭제) | - |
| `AFP1-H4-S1.retro*draft` | `AFP1-H4` 회고 정리가 공개 글을 늘린다 | 고른 회고에서 반복되는 배움을 찾고(근거: 어느 회고인지), 골라서 공개 글 초안 생성. 초안은 처음에 나만 보기로 저장 | 각 배움에 "몇 편에서 나왔는지"와 근거가 보인다. 초안을 글쓰기로 보내면 발행 전 점검이 먼저 돈다 | `AFR-04` | P2 |

### 5.4 화면 문구 가이드

AI 기능은 "AI가 만든 것"이 분명해야 하므로 표시와 안내 문구를 정합니다. 기존 말투(해요체, 쉬운 말)를 유지합니다.

| 위치 | 문구 |
|---|---|
| 관리자 화면의 AI 제안 | "AI 초안" 표시 + [적용] 버튼. 안내: "이 표시가 붙은 것은 AI가 만든 제안이에요. 저장하거나 공개되는 것은 내가 [적용]을 누른 것만이에요." |
| 방문자 화면의 요약 | "AI 요약" 표시. 안내: "AI가 만든 요약이에요. 틀릴 수 있어서 본문을 기준으로 봐 주세요." |
| 방문자 화면의 추천 | "내용이 비슷한 순서" 표시(AI를 쓰지 않아 "AI 추천"이라 하지 않음) |
| 발행 전 점검 단계 | "해결 필요"(발행 막음), "확인 필요"(확인했어요를 눌러야 함), "수정 권장"(알려 주기만) |
| 점검 탭 위쪽 요약 | "N/5 통과 · 해결 필요 N건 · 확인 필요 N건" / "발행할 수 있어요." (발행 버튼은 끄지 않고, 막히면 이 탭이 열림) |
| 기다리는 중 | "본문을 읽고 있어요…" |
| AI 오류 | "AI가 지금 응답하지 않아요. 글쓰기와 발행은 그대로 할 수 있어요. 잠시 뒤 다시 눌러 주세요." |
| 용어 규칙 | "AI 초안"은 내가 확인하기 전의 것, "요약"·"추천"은 내가 [적용]해서 공개된 것. "점검"은 찾아서 알려 주는 것이고 고치는 것은 항상 내가 한다 |

### 5.5 예상 성과

이 개선으로 글을 올리는 시간이 줄고, 공개 글에 요약이 비는 일과 채우지 않은 칸·개인정보가 남는 일이 없어지며, 방문자는 글의 핵심과 이어 읽을 글을 바로 볼 수 있게 됩니다. 방문자 수가 아직 적으므로 성과는 **운영자 쪽 지표(요약 채움률, 위반 0건, 적용률)**를 먼저 판단하고, 방문 기반 지표는 측정 4주 뒤에 기준값을 확정합니다.

#### OKR

| 구분 | 내용 | 현재 | 목표 | 연결 |
|---|---|---|---|---|

### 6.3 AI 호출 방식과 데이터

AI 서비스의 키는 날씨·고양이 API처럼 **서버 보안 설정에만 두고**, 화면(브라우저)에서는 직접 부르지 않습니다. 호출은 서버 함수가 관리자 로그인 표시를 확인한 뒤에만 합니다.

| 기능 | AI로 보내는 것 | 돌려받는 것 | 저장 위치 | 공개 여부 |
|---|---|---|---|---|
| 글쓰기 보조 (`AFR-01`, `AFR-02`) | 본문 텍스트 | 요약·설명·제목 제안 | 적용한 값만 글 데이터 | 적용한 글이 공개될 때만 |
| 첨부 요약 (`AFR-03`) | (삭제됨) | - | - | - |
| 회고 정리 (`AFR-04`, `AFR-05`) | 고른 회고 텍스트(선택에 따라 내가 고른 문장 요약만) | 배움 목록, 초안 | 초안은 나만 보기 글 | 내가 공개로 바꿀 때만 |
| AI 문맥 점검 (`AFR-08`) | 본문·제목·한 줄 요약 텍스트 | 의심 표현 목록 | 저장하지 않음(화면에서만) | 공개되지 않음 |
| 3줄 요약 (`AFR-09`) | 글 본문 | 개조식 3줄 | 글 데이터(`aiSummary`) | 체크해야 공개 |
| 관련 글 (`AFR-11`) | AI로 보내지 않음(서버가 글자 유사도로 계산) | 비슷한 글 순서 | 저장 안 함 | 공개 글끼리만 |

**보내지 않는 것:** 방문자의 이름·이메일·댓글, 관리자 계정 정보, API 키.

### 6.4 발행 전 점검 규칙

| 점검 항목 | 단계 | 방식 | 찾는 예 | 고치는 방법 안내 |
|---|---|---|---|---|
| 채우지 않은 칸 | 해결 필요 | 규칙 | `[이름]`, `[샘플]`, `[이메일 주소]` | 실제 내용으로 바꾸거나 지운다 |
| 오탈자·어색한 문장 | 수정 권장 | AI (`AFR-08`) | 맞춤법·띄어쓰기 오류 | 제안대로 고치거나 그대로 둔다(막지 않음) |
| 제목·요약과 본문의 일치 | 수정 권장 | AI (`AFR-08`) | 제목·한 줄 요약이 본문과 다른 내용 | 제목이나 요약을 본문에 맞춘다(막지 않음) |
| 개인정보·고객정보 | 전화번호는 해결 필요, 나머지는 확인 필요 | 전화번호는 규칙, 실명·소속·주소·고객사는 AI | `010-0000-0000`, "김OO 매니저님" | 연락처는 지우고, 동의 여부를 확인하거나 "동료 PM"처럼 바꾼다 |
| 회사 내부 자료 | 확인 필요 | AI (`AFR-08`) | "A사 내부 자료", "대외비" | 공개 가능한 자료인지 확인하고, 아니면 일반적인 설명으로 바꾼다 |

정확한 수치는 운영자 요청으로 점검에서 뺐습니다(12장 기획 3 답변). 점검은 5가지를 항상 보여 주고 항목마다 통과 여부와 "N/5 통과"를 표시합니다. 공개 글로 저장할 때는 화면과 보안 규칙(`firestore.rules`의 `publishable()`)이 같은 기준(채우지 않은 칸·전화번호)으로 막습니다.

점검 결과가 "해결 필요 0건, 확인 필요 항목 모두 확인"일 때만 공개 글로 저장됩니다(수정 권장은 막지 않음). 규칙 점검은 AI 없이도 되도록 만들고, AI 점검은 규칙이 놓치는 문맥 위험을 **보완**하는 용도입니다(AI가 틀릴 수 있으므로 최종 확인은 사람이 합니다).

### 6.5 유즈케이스 시나리오

**S1. 운영자가 글을 쓰고 공개**

1. 본문을 쓰고 AI 도우미의 "글쓰기 보조"를 누른다
2. 제목 후보와 한 줄 요약을 보고 마음에 드는 것만 [적용]한다
3. 발행 전 점검에서 `[이름]`(해결 필요)과 "김OO 매니저님"(확인 필요)이 나온다
4. 이름을 바꾸고, 실명은 동의를 확인한 뒤 "확인했어요"를 누른다
5. 점검을 통과하면 [발행]이 켜지고, 발행한다

남는 데이터: 제안·적용·무시·점검 기록(본문 제외)

**S2. (삭제됨) 운영자가 첨부 파일을 올려 요약**

첨부 파일 요약 기능을 삭제해서 이 시나리오도 뺐다. 첨부는 파일을 올리고 방문자가 내려받는 것까지만 된다.

**S3. 운영자가 회고를 공개 글로 정리**

1. 관리자 메뉴 RETRO SUMMARY에서 회고 3편을 고른다
2. "원문 문장 그대로 쓰지 않기"를 켜고 [반복되는 배움 찾기]를 누른다
3. 배움 3가지와 근거(어느 회고인지)를 보고 쓸 것만 고른다
4. [공개 글 초안 만들기] → 제목·요약·본문 초안이 나온다
5. [글쓰기로 보내기] → STUDY·공개로 채워지고, 발행 전 점검을 거친 뒤 저장한다

남는 데이터: 회고 정리 기록(원문 제외), 저장한 글

**S4. 방문자가 글을 읽음**

1. 글을 열면 위쪽에 "AI 요약" 3줄이 있고, 펼치거나 접을 수 있다
2. 본문을 읽고 아래의 "이어서 읽을 글" 카드에서 다음 글로 이동한다

남는 데이터: `summary_toggle`, `select_content`(`location=related`), `post_read`. 방문자 열람 중에는 AI가 호출되지 않는다.

### 6.6 범위 제외 (Out of Scope)

- 댓글 자동 분류·답글 초안(방문자가 쓴 댓글을 외부 AI로 보내야 해서 개인정보·악용 통제가 먼저 필요)
- 방문자 질문 답변(블로그 챗봇, 호출 비용과 악용을 막을 장치가 먼저 필요)
- 영어 번역
- AI가 글을 자동으로 발행·수정·삭제하는 기능(AI는 제안만 한다)
- 방문자 개인별 맞춤 추천(방문자 행동 추적이 필요해 이번에는 내용 유사도만 쓴다)

### 9.2 출시 방식 및 일정

- Phase마다 나눠서 배포한다. 화면 코드와 서버 함수 변경은 배포가 필요하다 (`node build.js --ssr` 후 규칙, 함수, 사이트 순서).
- 보안 규칙(`aiLogs`, 요약 승인 필드)을 바꾸는 Phase A는 규칙 배포 → 로그인 없이·방문자 계정으로 거부 시험 → 화면 배포 순서로 진행한다.
- AI 키는 운영자가 터미널에서 직접 저장하고(채팅에 쓰지 않는다), 배포 뒤 키 값을 출력하지 않고 호출 결과로만 확인한다.
- Phase B 배포 후 2주간 안정화 기간에 제안 품질과 적용률을 보고 문구·프롬프트를 보정한다. Phase C는 이 결과를 보고 진행 여부를 정한다.

## 부록. 용어와 변경 이력

### 용어

| 용어 | 설명 |
|---|---|
| AI 초안 | AI가 만든 제안. 내가 [적용]하기 전까지는 글에 반영되지 않는다 |
| 규칙 점검 | AI 없이 정해 둔 규칙(패턴)으로 찾는 점검. 채우지 않은 칸, 전화번호 |
| AI 문맥 점검 | 문맥이 필요한 것(오탈자, 제목·요약 일치, 개인정보, 내부 자료)을 AI가 찾는 점검. 규칙 점검을 보완한다 |
| 발행 게이트 | 점검을 통과해야만 발행되게 하는 단계 |
| 미리 생성 | 방문자가 열 때가 아니라 관리자가 글쓰기 화면에서 AI를 불러 만든 결과를 글 데이터에 저장해 두는 방식. 방문자가 늘어도 비용이 늘지 않는다 |
| 수정 권장 | 점검 단계의 하나. 알려 주기만 하고 발행을 막지 않는다(오탈자, 제목·요약 일치) |
| 이용 기록 | AI 제안·적용·무시 횟수 같은 숫자만 남기는 기록. 본문은 저장하지 않는다 |
| 최종 문제 (AFP) | 처음 발굴한 문제들을 비슷한 것끼리 묶은 4개의 핵심 문제 |
| RICE / MoSCoW | 우선순위 결정 방법. RICE는 점수식, MoSCoW는 Must·Should·Could·Won't 분류 |
