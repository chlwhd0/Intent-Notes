## 2. 개요

**배경.** 1차 개선으로 블로그는 관리자 글쓰기, 방문자 구글 로그인과 댓글, 조회수, 공유하기, 이미지·파일 첨부, GA4 연결까지 갖췄습니다. 그런데 "어떤 글이 인기 있는가"를 판단하려고 GA4를 열어 보면, 글이 **열렸는지**는 보이지만 **읽혔는지(완독)**, **반응을 이끌었는지(댓글·공유·좋아요·스크랩)**는 보이지 않습니다.

**문제.** 사이트의 핵심 행동(읽기, 댓글, 공유, 검색)이 페이지 안에서 일어나 주소가 바뀌지 않기 때문에 GA4의 자동 측정에 잡히지 않습니다. 글 주소가 글 번호라서 메뉴별 비교도 어렵고, 좋아요·스크랩은 기능 자체가 없으며, 운영자의 방문이 통계에 섞이는 경로도 남아 있습니다.

**솔루션.**

1. GA4로 보내는 이벤트와 파라미터를 설계해 완독·댓글·공유·글 선택 위치·검색·로그인·첨부 다운로드를 측정합니다.
2. 좋아요와 스크랩 기능을 만들어 "반응" 지표를 확보합니다.
3. GA 콘솔 설정과 월간 분석 대시보드를 갖춰 인기 글을 **몰입·반응·확산** 세 축으로 판단할 수 있게 합니다.

## 3. 문제

### 3.1 데스크리서치 (참고, 생략 가능)

1인 운영 블로그이므로 시장조사 대신 "현재 분석 체계의 진단(SWOT)"과 "분석 도구 관점의 3C"로 정리했습니다. 이번 범위(블로그 개선)에서는 건너뛰어도 되며 참고용으로 둡니다. 경쟁 서비스 항목은 일반적으로 알려진 수준이며, 서비스별 세부 기능은 후속 확인이 필요합니다.

#### 3.1.1 SWOT 분석 (블로그 분석 체계 기준)

| 강점 (Strength) | 약점 (Weakness) |
|---|---|
| 페이지마다 고유 주소가 있고 서버가 완성된 HTML을 그려서 GA4의 `page_view`가 정확하다<br>GA4 연결과 실시간 수신이 확인되었다<br>조회수, 댓글 같은 자체 데이터를 데이터베이스(Firestore)에 가지고 있다<br>관리자 브라우저 제외 로직과 이벤트 설계 문서(택소노미 v1.0)가 있다 | 완독, 댓글, 공유(링크 복사), 글 선택 위치, 검색어, 로그인이 GA4에 없다<br>좋아요, 스크랩 기능이 없어 측정할 대상 자체가 없다<br>글 주소가 글 번호라 GA에서는 페이지 제목으로만 구분되고, 메뉴별 비교가 안 된다<br>직접 센 조회수와 GA 숫자가 서로 다른 장부다<br>GA 콘솔 설정(맞춤 정의, 핵심 이벤트, 데이터 보관)이 아직 되어 있지 않다<br>분석·개발 리소스가 1인 운영이라 제한적이다 |

| 기회 (Opportunity) | 위협 (Threat) |
|---|---|
| 이벤트 몇 개만 추가해도 인기 글을 몰입·반응 기준으로 판단할 수 있다<br>Looker Studio(GA4 연결)로 무료 월간 대시보드를 만들 수 있다<br>좋아요·스크랩은 재방문과 충성도의 신호가 된다<br>구글·네이버 검색 등록 후 유입이 늘면 분석 가치가 커진다 | 광고 차단, 측정 거부 방문자는 GA에 잡히지 않는다<br>스크랩 목록 등 저장하는 개인정보가 늘어난다(처리방침 갱신 필요)<br>맞춤 측정기준은 등록 이후에만 쌓이고 소급되지 않는다 (등록이 늦을수록 데이터 손실)<br>방문자가 적을 때 순위를 믿고 판단하면 잘못된 결론이 난다 |

#### 3.1.2 3C 분석

| 구분 | 내용 | 시사점 |
|---|---|---|
| 고객 (Customer) | 운영자: 다음에 쓸 글을 데이터로 정하고 싶다<br>방문자(채용 담당자, 동료 PM): 글의 반응(좋아요, 댓글)으로 글의 가치를 가늠하고, 마음에 드는 글을 저장해 두고 싶다 | 운영자용 분석(GA)과 방문자용 반응 표시(좋아요·스크랩 수)를 따로 설계한다 |
| 경쟁 (Competitor) | 플랫폼 블로그(네이버 블로그, 티스토리 등)는 조회, 유입 경로, 공감(좋아요), 댓글 같은 통계를 운영 화면에서 기본 제공하는 것으로 알려져 있다<br>범용 분석 도구(GA4)는 자유도가 높지만, 무엇을 볼지 직접 설계해야 보인다 | 직접 만든 블로그의 약점은 "기본 통계가 없다"는 점이므로, 측정 설계가 곧 제품 기능이다 |
| 자사 (Company) | 직접 개발한 블로그. 화면·데이터·측정을 모두 마음대로 바꿀 수 있고 배포 없이 글이 반영된다. 반면 모든 측정을 직접 심어야 한다 | 측정 설계를 한 번 정리해 두면 이후 글이 늘어도 그대로 쓸 수 있다 |

### 3.2 문제 발굴

처음 발굴한 문제 15개입니다. 3.4에서 4개의 최종 문제로 묶습니다.

| ID | 문제 | 근거 | 해결 방향 |
|---|---|---|---|
| `PRB-01` | 완독을 정확히 알 수 없다 | GA 기본 scroll은 페이지 전체 높이의 90%에서만 1회 발생한다. 한 화면에 들어오는 짧은 글은 아예 발생하지 않고, 본문 아래 첨부·이전/다음·댓글 때문에 90% 지점이 본문 끝과 다르며, 빨리 내려도 발생한다 | 본문 기준 진행도(`read_progress`)와 완독(`post_read`) 이벤트 |
| `PRB-02` | 댓글이 GA에 없다 | 댓글은 데이터베이스에만 저장되고 GA로 보내지 않는다 | `comment_submit` 이벤트 |
| `PRB-03` | 공유가 일부만 잡힌다 | 공유 링크 3개(X, Facebook, LinkedIn)는 "외부 링크 click"에 섞여 잡히고, 링크 복사는 전혀 안 잡힌다 | `share` 이벤트(방법 구분) |
| `PRB-04` | 좋아요·스크랩 기능이 없다 | 기능이 없어 측정 불가. 반응을 볼 수 있는 신호가 댓글과 공유뿐이다 | 좋아요, 스크랩 기능 신설과 이벤트 |
| `PRB-05` | 메뉴별·글별로 안정적으로 집계할 수 없다 | 글 주소가 글 번호이고 GA에서는 페이지 제목으로만 구분된다. 제목을 바꾸면 한 글이 둘로 갈라진다. 메뉴 정보는 GA에 전달되지 않는다 | 글 번호(`post_id`)와 콘텐츠 그룹(메뉴)을 모든 이벤트에 첨부 |
| `PRB-06` | 어디서 글을 골랐는지 모른다 | 첫 화면 타일, 첫 화면 목록, 메뉴 목록, 이전·다음 링크 중 어디가 쓰이는지 구분되지 않는다 | `select_content` + 위치(`location`) |
| `PRB-07` | 검색어를 알 수 없다 | 목록 검색은 주소가 바뀌지 않아 GA의 사이트 검색으로 잡히지 않는다 | `search` 이벤트 |
| `PRB-08` | 로그인과 회원 구분이 안 보인다 | 구글 로그인 성공, 로그인한 방문자와 아닌 방문자의 차이가 GA에 없다 | `login` 이벤트 + 사용자 속성 `member_status` |
| `PRB-09` | 첨부 파일 다운로드가 불완전하다 | GA 자동 파일 다운로드는 확장자 목록 기반이라 한글(hwp) 등이 빠질 수 있고, 어느 글의 첨부인지도 알 수 없다 | `attachment_download` 이벤트 |
| `PRB-10` | 내 방문이 통계에 섞인다 | 관리자 로그인 표시가 있는 브라우저만 측정에서 빠지고, 로그아웃하면 그 표시도 지워져 이후 내 방문이 측정된다 | 소유자 브라우저 표시를 로그아웃 후에도 유지 + GA 내부 트래픽 필터 |
| `PRB-11` | 로그인·로그아웃 때 `page_view`가 한 번 더 잡힌다 | 로그인·로그아웃 직후 같은 페이지를 새로고침하기 때문이다 | 새로고침 없이 화면만 갱신 |
| `PRB-12` | GA 콘솔 설정이 비어 있다 | 맞춤 측정기준 미등록, 핵심 이벤트 미지정, 데이터 보관 기본값(짧음), 내부 트래픽 필터 없음, 향상된 측정 확인 안 함 | GA 콘솔 설정 체크리스트 수행 |
| `PRB-13` | 분석을 보는 화면이 없다 | GA 화면을 매번 직접 조합해야 하고, 자체 데이터(댓글 수 등)는 관리자 화면에서 볼 수 없다 | 월간 인기 글 대시보드(Looker Studio) + 관리자 글 목록에 반응 열 추가 |
| `PRB-14` | 측정하는 정보가 처리방침에 반영되어야 한다 | 좋아요·스크랩은 계정 식별 번호와 글 번호를 저장하므로 개인정보 처리방침 갱신이 필요하다 | 처리방침 문구 갱신 |
| `PRB-15` | 글 길이가 달라 읽기율·체류 시간을 공정하게 비교할 수 없다 | 짧은 글은 금방 읽혀 체류 시간이 짧다. 글 글자 수가 GA에 전달되지 않아 "체류 시간이 짧다 = 인기 없다"로 오판할 수 있다 | 글 글자 수를 이벤트에 함께 보내고, 글 길이 구간별 읽기율과 "길이 대비 참여 시간"을 지표로 정의 |

### 3.3 문제 검증

운영자가 알고 싶은 지표를 GA4에서 실제로 볼 수 있는지 점검하는 방식으로 검증했습니다(코드 확인, GA 이벤트 체계 점검, 실시간 수신 확인).

#### 3.3.1 점검 결과 및 인사이트

| # | 운영자가 알고 싶은 지표 | GA4 현재 | 근거 | 연결 문제 |
|---|---|---|---|---|
| 1 | 홈 화면 방문자 수 | 가능 | `page_view`와 사용자 수가 자동으로 쌓인다 (홈 두 주소 문제는 고침, 이전 데이터만 두 줄) | - |
| 2 | 페이지별 방문자 수 | 가능 | 페이지 및 화면 보고서 | - |
| 3 | 지역·기기·OS 정보 | 가능 | 자동 수집 측정기준 | - |
| 4 | 평균 체류(참여) 시간 | 가능 | `user_engagement` 기반 평균 참여 시간 (탭만 켜 둔 시간은 제외) | - |
| 5 | 완독 여부 | 부분 | scroll 90% 한계 | `PRB-01` |
| 6 | 댓글을 이끌어 냈는가 | 불가 | GA로 전송하지 않음 | `PRB-02` |
| 7 | 공유를 이끌어 냈는가 | 부분 | 링크 복사 누락 | `PRB-03` |
| 8 | 좋아요를 이끌어 냈는가 | 불가 | 기능 없음 | `PRB-04` |
| 9 | 스크랩을 이끌어 냈는가 | 불가 | 기능 없음 | `PRB-04` |

**인사이트:** 필수 지표 9개 중 GA4에서 확인 가능한 것은 4개(44%), 부분 가능이 2개, 불가가 3개입니다. 확인 가능한 4개는 모두 "열렸나"에 관한 것이고, 인기 글 판단에 필요한 **읽혔나(몰입)**와 **반응했나**는 비어 있습니다.

### 3.4 문제 최종 정의

#### 3.4.1 우선순위 결정 (RICE + MoSCoW)

RICE = Reach(영향 범위, 10점 만점) × Impact(영향도, 0.25~3) × Confidence(확신도) ÷ Effort(공수, 인일). 모든 수치는 기획자 추정치이며 방문 데이터가 쌓이면 보정합니다.

| 과제 | 최종 문제 | R | I | C | E | RICE | MoSCoW |
|---|---|---|---|---|---|---|---|
| `PRB-12` GA 콘솔 설정 (맞춤 정의 등) | `FP4` | 10 | 2 | 90% | 0.5 | 36.0 | Must |
| `PRB-10` 내 방문 제외 강화 | `FP4` | 10 | 1 | 90% | 0.5 | 18.0 | Must |
| `PRB-05` 글 번호·메뉴를 모든 이벤트에 첨부 | `FP1` | 8 | 2 | 90% | 1 | 14.4 | Must |
| `PRB-15` 글 길이 대비 읽기율 (글자 수 전송 + 지표 정의) | `FP1` | 8 | 1 | 70% | 0.5 | 11.2 | Should |
| `PRB-01` 완독 측정 (본문 기준) | `FP1` | 8 | 3 | 80% | 2 | 9.6 | Must |
| `PRB-02`·`PRB-03` 댓글·공유 이벤트 | `FP2` | 7 | 2 | 90% | 1.5 | 8.4 | Must |
| `PRB-13` 월간 대시보드, 관리자 글 목록 반응 열 | `FP4` | 5 | 2 | 70% | 1 | 7.0 | Should |
| `PRB-06` 글 선택 위치 이벤트 | `FP3` | 6 | 1 | 80% | 1.5 | 3.2 | Should |
| `PRB-11` 로그인 시 새로고침 제거 | `FP4` | 3 | 0.5 | 90% | 0.5 | 2.7 | Should |
| `PRB-07`·`PRB-08` 검색어, 로그인 이벤트 | `FP3`·`FP2` | 3 | 1 | 80% | 1 | 2.4 | Should |
| `PRB-04` 좋아요·스크랩 기능 신설 * | `FP2` | 6 | 2 | 60% | 5 | 1.4 | Must |
| `PRB-14` 처리방침 갱신 * | `FP2` | - | - | - | 0.5 | - | Must |
| `PRB-09` 첨부 다운로드 이벤트 | `FP3` | 2 | 1 | 70% | 1 | 1.4 | Could |
| 동의 방식(Consent Mode), 서버 측 측정, BigQuery 연동 | - | 2 | 1 | 50% | 2 | 0.5 | Won't |

\* `PRB-04`는 RICE 점수는 낮지만 운영자가 직접 요청한 지표(좋아요, 스크랩)라서 Must로 올렸습니다. `PRB-14`는 점수 대신 개인정보 준수 의무로 Must입니다. Won't 항목은 이번 범위에서 제외하며 사유는 9장에 적었습니다.

#### 3.4.2 문제 최종 정의

처음 발굴한 문제 15개를 **4개의 최종 문제**로 묶었습니다.

| 최종 문제 | 한 문장 정의 | 묶인 문제 (처음 15개 중) | 선정 이유 |
|---|---|---|---|
| `FP1` **몰입** | 글이 열렸는지는 보이지만, 글 길이까지 고려해 **끝까지 읽혔는지**는 알 수 없다 | `PRB-01` `PRB-05` `PRB-15` | 인기 글 판단의 첫 축. 필수 지표 5(완독)가 부분 가능에 그침 |
| `FP2` **반응** | 방문자의 **반응**(댓글·공유·좋아요·스크랩·로그인)이 측정되지 않거나 기능이 없다 | `PRB-02` `PRB-03` `PRB-04` `PRB-08` `PRB-14` | 인기 글 판단의 둘째 축. 필수 지표 6~9 중 3개 불가, 1개 부분 |
| `FP3` **탐색** | 방문자가 글을 **어디서·어떻게 찾는지**(선택 위치·검색어·첨부) 알 수 없다 | `PRB-06` `PRB-07` `PRB-09` | 몰입·반응이 어디서 시작되는지 설명하는 보조 축 |
| `FP4` **데이터 신뢰·활용** | 측정 데이터가 **오염되고** 콘솔 설정이 비었으며, 결과를 볼 **화면이 없다** | `PRB-10` `PRB-11` `PRB-12` `PRB-13` | 소급이 안 되므로 늦을수록 데이터 손실. 모든 분석의 바탕 |

**핵심 문제:** 인기 글을 판단하는 데 필요한 "몰입(읽혔나)"과 "반응(좋아요·댓글·공유·스크랩)"이 GA4에서 측정되지 않아, 지금은 "열린 횟수"로밖에 인기를 말할 수 없다.

**이번에 제외한 것:** 동의 방식(Consent Mode), 서버 측 측정, BigQuery 연동(공개 초기라 효용 대비 비용·복잡도가 큼), 글 내용 분석(키워드 등).

## 4. 가설 및 지표

최종 문제마다 가설을 세우고, 가설마다 확인할 지표를 정했습니다. 가설 ID는 부모 최종 문제를 앞에 붙였습니다. **신규**는 이번 개정에서 `FP4`(데이터 신뢰·활용)에 걸 가설이 없어 새로 추가한 가설입니다.

| 최종 문제 | 가설 ID | 가설 | 지표 | 측정 방법 |
|---|---|---|---|---|
| `FP1` 몰입 | `FP1-H1` | 본문 끝까지 읽히는 글이 따로 있고, 그것은 조회수 순위와 다르다 | 읽은 글 수(`post_read` 사용자)<br>읽기율 = 읽은 사용자 ÷ 글 열람 사용자 | GA 이벤트 보고서, 탐색 보고서 |
| | `FP1-H2` | 글 길이를 고려하면 "체류 시간이 짧아 보이던 글"의 평가가 달라진다 (짧은 글은 짧게 읽혀도 완독일 수 있다) | 글 길이 구간별 읽기율 (짧음 1,000자 미만 / 보통 1,000~3,000자 / 김 3,000자 이상)<br>길이 대비 참여 시간 = 평균 참여 시간 ÷ 예상 읽기 시간 (글자 수 ÷ 분당 500자) | `post_read` + 글 글자 수(맞춤 측정항목) + 평균 참여 시간, 대시보드 필터 |
| `FP2` 반응 | `FP2-H1` | 오래 머무는 글이 반응(댓글, 공유)도 많이 이끈다 | 평균 참여 시간<br>반응률 = (댓글 + 공유 + 좋아요 + 스크랩) 사용자 ÷ 읽은 사용자 | GA 보고서 + 대시보드 |
| | `FP2-H2` | 좋아요는 가볍게, 스크랩은 신중하게 쓰인다 (스크랩한 글이 재방문과 연결된다) | 글별 좋아요 수, 스크랩 수<br>스크랩한 방문자의 재방문율 | GA 이벤트 + 관리자 화면 |
| | `FP2-H3` | 로그인 안내가 있으면 댓글 전에 로그인하는 방문자가 는다 | 로그인 전환 = `login` 사용자 ÷ 글 열람 사용자<br>로그인 후 댓글 전환 | GA 이벤트 + 사용자 속성 |
| `FP3` 탐색 | `FP3-H1` | 첫 화면 타일이 목록보다 글 선택에 효과적이다 | 위치별 선택률 = `select_content` ÷ 해당 화면 조회 | GA 이벤트(`location`) |
| | `FP3-H2` | 검색은 찾으려는 글이 없을 때 쓰인다 | 결과 0건 검색 비율, 상위 검색어 | GA `search` 이벤트 |
| | `FP3-H3` | 자료 첨부가 있는 글은 내려받기가 많다 | 글별 첨부 내려받기 수, 내려받은 사용자 비율 | GA `attachment_download` |
| `FP4` 신뢰·활용 | `FP4-H1` | 소유자 브라우저 표시를 유지하고 내부 트래픽 필터를 켜면 내 방문이 통계에 섞이지 않는다 **(신규)** | 관리자 방문 혼입 건수 (목표 0) | DebugView, 탐색 보고서 |
| | `FP4-H2` | 로그인·로그아웃 새로고침을 없애면 같은 글의 `page_view` 중복이 사라진다 **(신규)** | 로그인 전후 같은 글 추가 `page_view` 건수 (목표 0) | DebugView |
| | `FP4-H3` | 콘솔 설정과 월간 대시보드가 갖춰지면 월 1회 인기 글 리포트를 정기 발행할 수 있다 **(신규)** | 월간 리포트 발행 횟수, 맞춤 정의 등록 수 (8+1) | 운영 기록, GA 콘솔 |

**인기 글 판단 방식 (v1 가설):** 점수 하나로 합치지 않고 세 축을 따로 순위로 봅니다. **몰입**은 "읽은 글 수"와 "읽기율"(글 길이 구간별 비교 포함), **반응**은 "반응률", **확산**은 "유입 소스·신규 사용자 비율"입니다. 점수화는 데이터가 쌓인 뒤 결정합니다.

## 5. 해결방안

### 5.1 솔루션 정의

**목표 문장:** "블로그 운영자가 GA4와 관리자 화면만으로, 어떤 글이 많이 열리고, 끝까지 읽히고, 반응(좋아요·댓글·공유·스크랩)을 이끌어 내는지 글별·메뉴별로 판단할 수 있게 한다."

해결방안 ID에는 부모 가설이 들어 있습니다. 예를 들어 `FP2-H2-S1.like`는 `FP2`(반응)의 `FP2-H2`(좋아요·스크랩 가설)에서 나온 첫 번째 해결방안입니다.

#### 최종 문제 FP1. 몰입

> 글이 열렸는지는 보이지만 끝까지 읽혔는지는 글 길이까지 고려해 알 수 없다.

| 해결방안 ID | 출발 가설 | 해결 방안 | 완료 기준 | 기능 | 우선 |
|---|---|---|---|---|---|
| `FP1-H1-S1.read*event` | `FP1-H1` 끝까지 읽히는 글은 조회 순위와 다르다 | 본문 기준 진행도(25·50·75·100%)와 완독 이벤트 `post_read` (글당 1회) | 짧은 글도 체류 시간이 차면 완독 발생. 빨리 내려만 간 경우는 발생 안 함. 중복 없음 | `FR-02` | P0 |
| `FP1-H1-S2.num*menu` | `FP1-H1` 끝까지 읽히는 글은 조회 순위와 다르다 | 글 번호(`post_id`)와 메뉴(콘텐츠 그룹)를 모든 글 이벤트에 첨부 | 모든 이벤트에 `post_id`가 붙고 GA에서 메뉴별로 나눠 볼 수 있다 | `FR-01` | P0 |
| `FP1-H2-S1.char*count` | `FP1-H2` 글 길이를 보면 평가가 달라진다 | 글 글자 수(100자 단위)와 예상 읽기 시간을 화면에 심어 이벤트로 전송 | 글 글자 수가 맞춤 측정항목으로 GA에 들어온다 | `FR-01` | P0 |
| `FP1-H2-S2.len*report` | `FP1-H2` 글 길이를 보면 평가가 달라진다 | 글 길이 구간별 읽기율, 길이 대비 참여 시간을 대시보드 필터로 제공 | 길이 구간별 읽기율을 한 화면에서 비교할 수 있다 | `FR-15` | P1 |

#### 최종 문제 FP2. 반응

| 해결방안 ID | 출발 가설 | 해결 방안 | 완료 기준 | 기능 | 우선 |
|---|---|---|---|---|---|
| `FP2-H1-S1.comment*event` | `FP2-H1` 오래 머무는 글이 반응도 많다 | 댓글·답글 저장 성공 직후 `comment_submit` 전송 | 저장 실패 시 미발생. 답글 여부(`is_reply`) 구분 | `FR-03` | P0 |
| `FP2-H1-S2.share*event` | `FP2-H1` 오래 머무는 글이 반응도 많다 | 링크 복사 성공, X·Facebook·LinkedIn 클릭 시 `share` 전송 (방법 구분) | 링크 복사도 잡히고 방법별로 구분된다 | `FR-04` | P0 |
| `FP2-H2-S1.like` | `FP2-H2` 좋아요는 가볍게, 스크랩은 신중하게 | 로그인한 방문자가 공개 글에 글당 1회 좋아요/취소. 합계 표시. `post_like` | 같은 계정 중복 불가(규칙으로 차단). 나만 보기 글에는 없음. 새로고침 후에도 합계 정확 | `FR-05` | P0 |
| `FP2-H2-S2.scrap` | `FP2-H2` 좋아요는 가볍게, 스크랩은 신중하게 | 스크랩/해제와 "내 스크랩" 목록 화면. `post_bookmark` | 목록은 본인만 볼 수 있다(규칙으로 차단). 글별 합계는 운영자만 확인 | `FR-06` | P0 |
| `FP2-H2-S3.privacy` | `FP2-H2` 좋아요는 가볍게, 스크랩은 신중하게 | 좋아요·스크랩이 저장하는 정보와 측정 이벤트를 처리방침에 추가 | 처리방침에 반영되고 푸터 링크에서 접근 가능 | `FR-13` | P0 |
| `FP2-H3-S1.login*event` | `FP2-H3` 로그인 안내가 로그인 전환을 늘린다 | 방문자 구글 로그인 성공 시 `login` 전송, 로그인 여부를 사용자 속성 `member_status`로 기록 | 이메일처럼 보이는 값은 전송 안 함 | `FR-08` | P1 |

#### 최종 문제 FP3. 탐색

> 방문자가 글을 어디서·어떻게 찾는지(선택 위치·검색어·첨부) 알 수 없다.

| 해결방안 ID | 출발 가설 | 해결 방안 | 완료 기준 | 기능 | 우선 |

#### 최종 문제 FP4. 데이터 신뢰·활용

> 측정 데이터가 오염되고 콘솔 설정이 비었으며 결과를 볼 화면이 없다.

| 해결방안 ID | 출발 가설 | 해결 방안 | 완료 기준 | 기능 | 우선 |
|---|---|---|---|---|---|
| `FP4-H1-S1.owner*mark` | `FP4-H1` 소유자 표시+필터로 내 방문이 안 섞인다 | 관리자로 한 번 로그인한 브라우저에 "소유자" 표시를 남기고 로그아웃해도 지우지 않음 | 관리자 로그아웃 후 열어도 이벤트가 GA에 안 들어온다 | `FR-10` | P0 |

### 5.4 화면 문구 가이드

분석 개선 프로젝트라 마케팅 카피 대신 새로 생기는 화면 문구와 용어 규칙을 정합니다. 기존 말투(해요체, 쉬운 말)를 유지합니다.

| 위치 | 문구 |
|---|---|
| 좋아요 버튼 (평상시) | "좋아요 12" |
| 좋아요 (내가 누름) | "좋아요 13" (강조), 다시 누르면 취소 |
| 스크랩 버튼 | "스크랩" / 저장되면 "스크랩함" |
| 로그인이 필요할 때 | "좋아요와 스크랩은 Google로 로그인하면 쓸 수 있어요. · 개인정보 처리방침" |
| 내 스크랩 비어 있음 | "아직 스크랩한 글이 없어요. 마음에 드는 글에서 '스크랩'을 눌러 보세요." |
| 용어 규칙 | "스크랩"은 내가 저장해 두는 것, "공유"는 다른 사람에게 보내는 것으로 구분해 쓴다. "방문자 수"와 "조회수"를 섞어 쓰지 않는다 |

### 5.5 예상 성과

이 개선으로 "인기 글"이 열린 횟수가 아니라 읽힌 정도와 반응으로 정의되고, 운영자가 글쓰기 방향(주제, 길이, 제목, 메뉴)을 데이터로 정할 수 있게 됩니다. 방문자 수가 아직 적으므로 성과는 분석 가능 범위(측정 커버리지)와 데이터 품질로 정하고, 방문 기반 수치는 측정 4주 뒤에 확정합니다.

### 6.5 유즈케이스 시나리오

**S1. 방문자가 글을 읽고 반응**

1. 첫 화면 타일을 눌러 글에 들어간다 (`select_content` 위치=`home_tile`)
2. 본문을 읽으며 진행도 이벤트가 쌓이고, 끝까지 읽으면 `post_read`
3. 공유하기에서 "링크 복사" (`share` method=`copy_link`)
4. 구글 로그인 후 댓글 등록 (`login`, `comment_submit`)

남는 데이터: 선택 위치, 완독, 공유 방법, 로그인, 댓글이 모두 같은 `post_id`로 연결됩니다.

**S2. 방문자가 좋아요·스크랩**

1. 로그인하지 않은 상태에서 좋아요를 누르면 로그인 안내가 나온다
2. 구글 로그인 후(새로고침 없이) 좋아요 + 스크랩
3. 사이드바 "내 스크랩"에서 저장한 글을 다시 연다

남는 데이터: `post_like`, `post_bookmark`(add), 재방문

**S3. 운영자가 월간 분석**

1. 대시보드에서 기간(지난 30일)과 메뉴를 고른다
2. 몰입 순위(읽은 글 수, 읽기율), 반응 순위(반응률), 확산(유입 소스)을 본다
3. 관리자 글 목록에서 댓글·좋아요·스크랩 수를 확인한다
4. 다음 글의 주제와 길이를 정한다

남는 데이터: 월간 리포트 메모 (의사결정 문서에 기록)

**S4. 운영자가 글을 확인**

관리자로 로그아웃한 뒤 공개 글을 열어도 측정되지 않습니다. 남는 데이터: 내 방문 혼입 없음.

| 방문자가 적어 순위가 믿을 수 없다 | 중간 | 조회 50 이상 글에만 비율 지표 순위를 쓴다. 적은 구간은 추세만 본다 |
| 좋아요·스크랩 규칙 오류로 데이터 위조나 개인 목록 노출 | 높음 | 규칙을 코드로 관리하고 거부 시험을 필수 완료 기준으로 둔다. 개인 목록은 본인만 읽도록 규칙으로 막는다 |
| 이벤트 중복 발생으로 숫자가 부풀려진다 | 중간 | 글당 1회 플래그, 새로고침 제거(`FR-09`), DebugView로 점검 |
| 광고 차단·측정 거부로 누락된다 | 낮음 | 절대 숫자보다 비율·추세로 판단한다. 자체 데이터(댓글·좋아요·스크랩 수)로 교차 확인한다 |
| 개인정보 항목이 늘어난다 | 중간 | 필요한 항목만 저장하고 처리방침을 함께 갱신한다. 이름·이메일·댓글 내용은 GA로 보내지 않는다 |
| 비용 증가 | 낮음 | 합계는 서버가 집계해 읽기를 줄이고, 월 1회 사용량을 점검한다 |
| 배포 후 문제 발생 | 중간 | 단계별 배포. 문제 시 직전 커밋으로 되돌려 다시 배포한다 (규칙은 직전 규칙 파일로 되돌림) |

## 부록. 용어와 변경 이력

### 용어

| 용어 | 설명 |
|---|---|
| 이벤트 | 방문자의 행동이 GA에 남는 단위 (예: 페이지 열기, 공유) |
| 파라미터 | 이벤트에 붙는 설명 (어느 글, 어느 위치 등) |
| 맞춤 측정기준 | 파라미터를 GA 보고서에서 쓰려면 등록해야 하는 이름표. 등록 시점부터 쌓이고 소급되지 않는다 |
| 핵심 이벤트 | 성과로 따로 집계하는 이벤트 (예전 이름 "전환") |
| 택소노미 | 이벤트와 파라미터의 이름·분류 체계 |
| RICE / MoSCoW | 우선순위 결정 방법. RICE는 점수식, MoSCoW는 Must·Should·Could·Won't 분류 |
| 최종 문제 (FP) | 처음 발굴한 문제들을 비슷한 것끼리 묶은 4개의 핵심 문제 |
