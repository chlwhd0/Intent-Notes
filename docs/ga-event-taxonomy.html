01 · 요약

지금 GA는 "어느 페이지를 열었나"만 안다

AS-IS

열었는지만 보인다

  • 방문자 수, 페이지별 조회, 지역·기기·OS는 이미 나온다.
  • 글을 읽었는지, 어디서 골랐는지, 공유·댓글·로그인은 보이지 않는다.
  • 메뉴(PORTFOLIO, STUDY…)별 비교도 안 된다.
TO-BE

이벤트 8개를 더한다

  • 탐색 3 · 읽기 2 · 공유 1 · 참여 1 · 계정 1
  • 공통 파라미터 6개 + 사용자 속성 1개
  • 핵심 이벤트 3개: post_read share comment_submit

이 설계로 답하게 되는 것

  • 어떤 글이 읽히는가 (열기가 아니라 읽기)
  • 사람들은 첫 화면 타일과 목록 중 어디서 글을 고르는가
  • 어떤 글이 공유·댓글을 만드는가
  • 로그인은 어느 글에서 일어나는가

결정이 필요한 것

① 글을 "읽었다"고 보는 기준(스크롤 50% 이상 + 30초 이상)을 이대로 갈지 · ② 방문 통계 안내(개인정보)와 동의 배너를 넣을지 · ③ 이벤트 구현을 P0(5개)부터 시작할지

알고 싶은 것 네 가지, 그리고 새로 생기는 질문

#알고 싶은 것왜 필요한가AS-ISTO-BE

2페이지별 방문자 숫자어느 화면이 열리는지 본다.가능가능 + 메뉴별 합계

4어떤 글을 가장 많이 읽는가다음에 무슨 글을 쓸지 정한다.부분 가능
"열었다"만		가능 "읽었다" 기준
5어디서 글을 고르는가첫 화면 타일, 첫 화면 목록, 메뉴 목록 중 어디가 잘 쓰이는지 본다.불가가능
6공유·댓글이 많은 글반응을 만드는 글의 공통점을 찾는다.불가가능

03 · AS-IS 진단

지금 쌓이는 것, 쌓이지 않는 것

보이는 것
  • page_view 홈·목록·글·소개 페이지를 열 때마다 (경로와 페이지 제목이 같이 남는다. 글 제목은 "제목 · Intent Notes" 형태)
  • 사용자 수, 세션, 참여 시간
  • 국가·도시, 기기 종류, OS, 브라우저, 유입 경로
  • scroll 페이지 끝(90%) 도달 시 1회
  • click 외부로 나가는 링크 (공유 링크 X·Facebook·LinkedIn 3개가 여기에 걸린다)
보이지 않는 것
  • 글을 읽었는지 (90% 도달 1회뿐, 중간 읽기와 체류는 구분 불가)
  • 글을 어디서 골랐는지 (타일, 목록, 이전·다음 글)
  • 메뉴별 합계 (글 주소가 글 번호라서 제목으로만 구분됨)
  • 검색어 (목록 검색은 주소가 바뀌지 않아 사이트 검색으로 잡히지 않는다)
  • 링크 복사 공유, 댓글 등록, 구글 로그인

구조적인 이유

① GA는 "페이지 열림"을 기본으로 세는데, 이 블로그의 핵심 행동(읽기, 공유, 댓글)은 페이지 안에서 일어난다. ② 글 화면의 조회수(직접 센 숫자)와 GA 숫자는 서로 다른 장부라 일치하지 않는다. 분석은 GA 한 곳을 기준으로 한다.

이름을 짓는 규칙 여섯 가지

#규칙
1소문자 snake_case, 40자 이하. 예 comment_submit
2GA 권장 이벤트가 있으면 그 이름을 쓴다. login share search select_content
3직접 지을 때는 "대상_동작". post_read comment_submit
4같은 뜻이면 같은 파라미터 이름. 글 번호는 항상 post_id, 메뉴는 항상 menu
5값은 고정 목록. location은 정해 둔 4가지만 보낸다. 자유 입력 금지
6개인정보를 보내지 않는다. 이름, 이메일, 댓글 내용, 계정 번호(uid) 제외

이렇게 짓는다 / 이렇게 짓지 않는다

location: home_tile"첫 화면에서 큰 사진 눌렀음"자유 문장은 집계가 안 됨

09 · 핵심 이벤트와 지표 정의

"읽었다"를 어떻게 정의하고, 무엇을 숫자로 볼까

핵심 이벤트 3개
  • post_read — 읽은 글. 이 블로그의 핵심 성과
  • share — 남에게 권한 글
  • comment_submit — 말을 걸게 만든 글

GA의 "핵심 이벤트(전환)"로 표시하면 보고서 전반에서 따로 집계된다.

"읽었다"의 기준 (제안)

스크롤 50% 이상 + 글 화면 체류 30초 이상. 둘 중 하나만으로는 읽은 것으로 보지 않는다(빨리 내려 본 사람, 열어만 두고 떠난 사람을 거른다). 측정 2주 뒤 분포를 보고 기준을 조정한다.

지표정의쓰임
홈 방문자경로 /의 사용자 수유입 규모
글 열람경로 /posts/*의 page_view열렸는지
읽은 글post_read 이벤트 수 (post_id별)글 순위
읽기율post_read 사용자 ÷ 글 열람 사용자글 품질 신호
위치별 선택률select_content ÷ 해당 화면 page_view (location별)첫 화면 개선
반응률(share + comment_submit) 사용자 ÷ post_read 사용자공감 신호
로그인 전환login 사용자 ÷ 글 열람 사용자댓글 기능 효과

10 · GA 화면

질문별로 GA의 어디를 보는가

#질문AS-IS: 지금 보는 곳TO-BE: 설계 후 보는 곳
1홈 방문자보고서 › 참여도 › 페이지 및 화면 · 페이지 경로 / 의 사용자그대로. 탐색 보고서의 퍼널 첫 단계로도 쓴다
2페이지별 방문자같은 화면에서 페이지 제목·경로별 조회수와 사용자그대로. menu를 더하면 메뉴별 합계
3지역·기기·OS보고서 › 사용자 › 인구통계 세부정보(국가·도시), 기술 세부정보(기기·OS·브라우저)그대로 (기본 수집)
4많이 읽은 글페이지 및 화면을 조회수순 정렬 — "열었다" 기준보고서 › 참여도 › 이벤트 › post_read › post_id / 탐색 › 자유 형식(행 post_id, 값 이벤트 수·사용자)
5어디서 글을 고르나보이지 않음이벤트 › select_content › location
6공유·댓글 많은 글보이지 않음이벤트 › share · comment_submit › post_id
7검색어보이지 않음이벤트 › search › search_term
-확인·검증보고서 › 실시간관리 › DebugView로 이벤트 하나하나 확인 + 실시간

일반 보고서는 반영에 하루쯤 걸리고, 실시간과 DebugView만 바로 보인다.

11 · GA 화면 설정

구현 전에 GA에서 한 번만 해 두는 일

관리 화면에서

  • 맞춤 정의 › 맞춤 측정기준 7개 등록 (post_id, menu, location, depth, method, is_reply · 사용자 범위 member_status)
  • 이벤트 › 핵심 이벤트로 표시: post_read share comment_submit (이벤트가 한 번 들어온 뒤에 표시 가능)
  • 데이터 수집 및 수정 › 데이터 보관: 이벤트 데이터 보관을 14개월로 (기본 2개월이면 탐색 보고서가 짧게 잘린다)
  • 데이터 스트림 › 향상된 측정: 페이지 조회·스크롤·이탈 클릭은 유지. 사이트 검색(주소 변화 없음)·양식 상호작용은 끈다
  • 데이터 수집 › Google 신호: 끔 (광고용)
  • 데이터 필터: 내부 트래픽(내 IP) 제외 (로그아웃 상태의 내 방문 제외)

탐색 보고서로 저장해 둘 것 2개

  • 글별 읽기 순위 — 행: post_id · 열: 메뉴 · 값: post_read 이벤트 수, 사용자, 읽기율
  • 방문→읽기→반응 퍼널 — 4단계(다음 쪽 도식). 기기 종류와 location으로 쪼개서 본다

확인은 이 순서로

  • 1) 관리 › DebugView에서 이벤트가 1번씩 들어오는지
  • 2) 맞춤 측정기준을 등록한 다음날 이벤트 보고서에서 post_id가 보이는지
  • 3) 1~2주 뒤 읽음 기준(50%·30초) 분포를 보고 조정

12 · AS-IS → TO-BE 도식 ③

"열었다"에서 "반응했다"까지, 퍼널로 본다

① 홈·목록 보기page_view
② 글 선택select_content
③ 읽음 ★post_read
④ 반응 ★share · comment_submit

막대 길이는 설명용이다. 실제 비율은 측정 2주 뒤에 채운다.

AS-IS

①과 "글 페이지 열림"만 알 수 있다. 열린 글 중 몇 %가 읽혔고, 어디서 나가는지 알 수 없다.

TO-BE

단계 사이의 이탈 지점이 보인다.

  • ②가 낮다 → 첫 화면 타일·제목·썸네일을 고친다
  • ②→③이 낮다 → 글의 첫 문단, 길이를 고친다
  • ③→④가 낮다 → 공유·댓글 안내 위치를 고친다
  • 모바일이 유독 낮다 → 모바일 화면을 먼저 고친다

13 · 개인정보와 검증

보내지 않을 것과, 제대로 보내는지 확인하는 법

개인정보 원칙

  • 이름, 이메일, 댓글 내용, 계정 번호(uid)는 GA로 보내지 않는다. 로그인 여부만 member_status로 보낸다.
  • 관리자가 로그인해 둔 브라우저는 측정하지 않는다(구현됨).
  • 검색어는 입력한 글자가 개인정보일 수 있어 소문자 50자까지만 보내고, 이메일처럼 보이는 값(@ 포함)은 보내지 않는다.
  • 광고용 신호(Google 신호)는 켜지 않는다.
  • 공개 전에 정할 것: 방문 통계 안내 문구(개인정보 처리방침)와 동의 배너 여부

완료 기준 (구현 후 DebugView로 확인)

  • 이벤트 8개가 각각 한 번만 들어온다(중복 없음)
  • 글당 post_read는 1번, read_progress는 깊이별 1번
  • 파라미터 값이 고정 목록 안에 있다(오타·자유 문장 없음)
  • 관리자 로그인 상태에서는 이벤트가 하나도 안 들어온다
  • 나만 보기 글·관리자 화면에서는 이벤트가 없다
  • 댓글 저장이 실패하면 comment_submit이 안 나간다
  • 측정 코드가 막혀도(광고 차단) 글 읽기·댓글은 정상 동작한다

순위이벤트구현 위치
P0select_content카드·타일 링크에 data-loc (서버가 그림) + 클릭 위임
P0read_progress post_read글 페이지 스크롤·체류 감시 (analytics.js)
P0shareshare.js: 복사 버튼과 공유 링크

공통 도우미 track(이름, 파라미터) 하나만 만들고, 측정 코드가 없거나 막혀 있으면 아무 일도 하지 않게 한다. 서버가 그리는 화면이 바뀌므로 서버 함수와 호스팅 배포가 필요하다.

리스크와 열린 결정

  • 숫자 불일치: 직접 센 조회수와 GA는 다르다 → 분석은 GA 기준으로 못박는다.
  • 누락: 광고 차단·동의 거부 방문자는 GA에 잡히지 않는다 → 절대 숫자보다 추세와 비율로 본다.
  • 읽음 기준: 50%·30초는 가설이다 → 2주 뒤 조정.
  • 소급 불가: 맞춤 측정기준은 등록 후부터 쌓인다 → 등록을 구현보다 먼저.
  • 글 주소가 글 번호: 제목을 바꿔도 번호가 같아 분석은 안정적이지만, 보고서에서 번호만 보면 알아보기 어렵다 → 페이지 제목과 함께 본다.
  • 결정 요청: 개인정보 안내와 동의 배너, P0 구현 착수

이벤트 하나는 이렇게 나간다

// 글 카드를 눌렀을 때 (첫 화면 큰 타일)
gtag('event', 'select_content', {
  post_id: 'nvVdCkqMDLS0qWodwc4b',
  menu: 'PORTFOLIO',
  location: 'home_tile'
});

// 글을 읽었다고 판단했을 때 (핵심 이벤트)
gtag('event', 'post_read', {
  post_id: 'nvVdCkqMDLS0qWodwc4b',
  menu: 'PORTFOLIO'
});

// 댓글 저장 성공 후
gtag('event', 'comment_submit', {
  post_id: '…', menu: 'STUDY', is_reply: false
});

이름, 이메일, 댓글 내용은 어느 이벤트에도 들어가지 않는다.

용어

  • 이벤트: 방문자의 행동 한 번 (예: 공유)
  • 파라미터: 이벤트에 붙는 설명 (예: 어느 글, 어느 메뉴)
  • 핵심 이벤트: 성과로 따로 집계하는 이벤트 (예전 이름 "전환")
  • 맞춤 측정기준: 파라미터를 GA 보고서에서 쓰려면 등록해야 하는 이름표
  • 택소노미: 이벤트와 파라미터의 이름·분류 체계
