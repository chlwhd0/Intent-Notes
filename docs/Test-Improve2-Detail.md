## 1. 기획 의도와 시험 기준

**이 블로그는** AI PM의 포트폴리오와 스터디 노트를 보여 주는 개인 블로그이고, 글 한 편이 **만들어져서 공개되고 읽히기까지**의 흐름에 AI를 붙여 보는 프로젝트입니다. PRD는 그 흐름의 문제를 네 가지로 정했습니다.

| 문제 | 한 문장 | 시험으로 확인한 것 |
|---|---|---|
| `AFP1` 작성 부담 | 요약·제목을 매번 손으로 쓴다 | 제안이 나오고, 쓸 만하게 반영되는가 |
| `AFP2` 공개 전 안전 | 사람의 눈으로만 공개 전에 확인한다 | 위험한 글이 공개되기 전에 막히는가 |
| `AFP3` 독자 이해·이어 읽기 | 핵심을 빨리 알고 이어서 읽을 글을 찾기 어렵다 | 요약과 추천이 독자에게 도움이 되게 보이는가 |
| `AFP4` AI 신뢰·통제 | AI 결과가 걸러지지 않고 비용·원문 전송이 통제되지 않는다 | 승인·거부·한도·기록·개인정보가 지켜지는가 |

**지켜야 할 원칙 셋:** ① AI는 제안만 하고 사람이 적용한다 ② 방문자가 글을 읽을 때는 AI를 부르지 않는다 ③ 규칙으로 되는 점검은 AI에 맡기지 않는다.

**성공 지표(KR):** KR1 한 줄 요약 채움률 100% · KR2 공개 화면의 빈칸·전화번호 0건 · KR3 AI 제안 적용률(4주 뒤 기준값) · KR4 방문자 열람당 AI 호출 0회

## 3. 시험 항목

### A. 독자가 보는 블로그 (포트폴리오·스터디가 잘 보이는가)

#### A1. 첫 화면이 이 블로그가 무엇인지 알려 준다 — ✅

- **입력:** 홈(`/`) 열기
- **기대값:** 블로그 이름, 한 줄 소개, 최근 글이 보이고 검색·공유용 정보(대표 주소, 공유 카드)가 있다
- **결과값:** [사이트] 이름 "Intent Notes", 소개 "AI PM의 포트폴리오, 회고, 그리고 일하며 배운 것들을 기록합니다.", 최근 글 5개, 대표 주소·공유 카드 있음, 푸터 "© 2026 Chris"

#### A2. 메뉴별 글 목록에 모든 글과 썸네일이 보인다 — ✅

- **입력:** `/portfolio/`, `/study/`, `/posts/` 열기
- **기대값:** 각 메뉴의 공개 글이 모두 나오고 썸네일이 있다
- **결과값:** [사이트] 포트폴리오 14편(썸네일 14), 스터디 17편(썸네일 15. 2편은 썸네일을 "없음"으로 고른 기존 글), 전체 31편

#### A3. 휴대폰에서 읽을 수 있다 — ✅

- **입력:** 폭 375px로 목록과 글 열기
- **기대값:** 가로 스크롤이 없고, 제목이 잘리지 않고, 요약 상자·추천 카드가 화면 안에 있다
- **결과값:** [사이트] 목록·글 모두 가로 넘침 없음, 썸네일 88×60, 제목 잘림 0, 요약 상자·추천 카드 폭 327px(화면 안), 본문 넘치는 요소 0. 참고: 요약 상자를 누르는 줄 높이는 28px(작은 편)

#### A4. 검색에 공개 글만 노출된다 — ✅

- **입력:** 사이트맵, RSS, 로봇 안내, 회고 주소, 관리자·404 화면 열기
- **기대값:** 공개 글 모두 사이트맵에 있고, 나만 보기(회고)·관리자는 없다. 관리자·404는 색인 차단
- **결과값:** [사이트] 사이트맵 37주소(글 31, 회고·관리자 없음), RSS 20항목(제목에 "회고"가 든 것은 샘플 글 1편뿐), `/retrospective/` 404, 관리자·404 화면 색인 차단 표시

### B. 독자 이해·이어 읽기 (`AFP3`, `AFR-09`~`11`)

#### B1. 글 위에 "AI 요약" 상자가 정직하게 보인다 — ✅

- **입력:** 3줄 요약이 승인된 글 열기
- **기대값:** 상자가 펼쳐져 있고, "AI" 배지·3줄·안내 문구가 있다
- **결과값:** [사이트] 해당 1편("PRD부터 배포까지…")에 상자 열림, AI 배지, 3줄, 안내 문구 모두 있음. 나머지 30편에는 상자 없음

#### B2. 승인한 3줄 요약은 보인다 — ✅

- **입력:** 3줄 요약을 만들고 "내가 확인했어요" 체크(본문 그대로)
- **기대값:** 글 상세에 AI 요약 상자가 보인다
- **결과값:** [코드] 상자 있음, AI 배지 있음

#### B3. 본문이 바뀌면 틀린 요약을 숨긴다 — ✅

- **입력:** 체크한 뒤 본문이 바뀜(저장된 지문과 현재 본문이 다름)
- **기대값:** 요약을 숨긴다
- **결과값:** [코드] 상자 없음

#### B4. 체크하지 않은 요약은 공개되지 않는다 — ✅

- **입력:** 요약은 만들었지만 "확인했어요"를 체크하지 않음
- **기대값:** 요약이 보이지 않는다(자동 공개 금지)
- **결과값:** [코드] 상자 없음

#### B5. 추천은 글이 충분할 때만 보인다 — ✅

- **입력:** 공개 글 3개 / 4개로 빌드
- **기대값:** 3개(다른 글 2개): 카드 숨김, 4개(다른 글 3개): 카드 최대 3개
- **결과값:** [코드] 3개일 때 카드 없음, 4개일 때 카드 3개

#### B6. 모든 글에 "이어서 읽을 글"이 붙는다 — ✅

- **입력:** 실제 글 31편 열기
- **기대값:** 카드가 최대 3개다
- **결과값:** [사이트] 31편 모두 카드 있음(3개 30편, 2개 1편), 최대 3개 지킴

#### B7. 관련 없는 글은 연결하지 않는다 — ✅

- **입력:** 공개 글 3개(AI PM 주제) + 4번째로 전혀 다른 주제(김치찌개 레시피)의 글 추가
- **기대값:** 김치찌개 글에는 추천 카드가 붙지 않는다
- **결과값:** [코드] 처음 시험에서는 **김치찌개 글에 카드 3개가 붙었음**(유사도 0.177. "입니", "니다", "에요" 같은 흔한 말투 조각이 겹쳐서). 흔한 조각을 덜 세도록 고치고(IDF 가중, 기준 0.04→0.055) 다시 시험: 4편일 때 카드 0개, 글 27편(샘플 글 전체)에 섞어도 0개, 정상 글 26편은 모두 카드 3개 유지. 배포 뒤 [사이트] 글 31편 중 27편이 카드 3개, 주제가 다른 글(호랑이·고양이·「PRD작성과 무료 API 활용」·「클로드 코드로 내 블로그 만들기」)만 1~2개로 줄어듦

#### B8. 추천된 글이 주제상 비슷하다(사람이 읽고 판단) — ⚠️

- **입력:** 실제 글 4편의 추천 카드 확인(추천 수정을 배포한 뒤 다시 확인)
- **기대값:** 주제가 이어지는 글이 나온다
- **결과값:** [사이트] 「프롬프트 기본기」→평가·PRD 체크리스트·에이전트(일치, 수정 전과 같음), 「발행 전 점검」→승인 원칙·고객 문의 요약 PRD 연습 사례·2차 개선 PRD(일치. 연습 사례는 연결이 약간 약함. 수정 전: 승인 원칙·PRD·PRD 체크리스트), 「LLM 기초」→환각·RAG·모델 선택(일치. 수정 전의 「AI PM이 하는 일」보다 주제가 더 가까움), 「모바일 관리자 화면」→측정 설계·비용 통제·Intent Notes 소개(약함, 수정 전과 같음. 화면 개선 글인데 측정·비용 글이 이어짐). 4편 중 3편 일치. 카드의 제목만 읽고 판단했고 본문 전체를 읽지는 않음

### C. 공개 전 안전 (`AFP2`, `AFR-06`~`08`)

#### C1. 규칙 점검이 빈칸 표시·전화번호를 정확히 찾는다 — ✅

- **입력:** 샘플 12건(빈칸 표시 3, 전화번호 형식 4, 둘 다 1, 정상 4: 날짜·사업자번호·`[참고]`·`[Claude Code]`)
- **기대값:** 12건 모두 맞게 판정
- **결과값:** [코드] 12/12 일치

#### C2. 해결 필요가 남은 글은 발행이 막힌다 — ✅

- **입력:** `[이름]` 표시와 전화번호가 든 글에서 [발행하기]
- **기대값:** 저장되지 않고, 점검 탭이 열리고, 이유를 알려 준다
- **결과값:** [사이트] 화면 그대로, "해결할 것이 2개 있어요" 안내, 점검 탭 자동 열림, 해결 필요 2건. 글은 저장되지 않음

#### C3. "확인 필요"는 확인하면 발행할 수 있다 — ✅

- **입력:** AI가 개인정보·내부 자료를 짚은 글에서 [발행하기] → "확인했어요" 2개 체크 → [발행하기]
- **기대값:** 확인 전에는 막히고, 확인 뒤에는 저장된다
- **결과값:** [로컬] 확인 전 "확인이 필요한 것이 2개" 안내로 막힘 → 확인 뒤 저장되어 글 보기로 이동

#### C4. "수정 권장"은 발행을 막지 않는다 — ✅

- **입력:** 오탈자·제목 불일치만 있는 글
- **기대값:** 막지 않는다
- **결과값:** [코드] 막힘 0개. [사이트] 실제 AI가 오탈자를 "수정 권장"으로 표시했고 발행 버튼은 켜져 있음

#### C5. 실제 AI가 위험한 표현을 짚는다 — ✅

- **입력:** "김OO 매니저님과 회의", "대외비라서 사내에서만 공유", "않돼서·헤맷지만"이 든 글
- **기대값:** 개인정보·내부 자료는 확인 필요, 오탈자는 수정 권장
- **결과값:** [사이트] 개인정보=확인 필요(김OO 매니저님…), 내부 자료=확인 필요(대외비…), 오탈자=수정 권장(기능이 않돼서 / 한참 헤맷지만), 빈칸·제목 일치=통과. 확인 모두 누르면 4/5 통과·남은 해결 필요 0

#### C6. 점검 정확도(표본 20건) — ✅

- **입력:** 문제 있는 글 12건 + 정상 글 8건
- **기대값:** 문제 10건 이상 찾고, 정상 글을 잘못 지적한 것 1건 이하(합격선)
- **결과값:** [사이트] 앞서 실시(같은 날): 문제 12/12 찾음, 오탐 0/8. 이번 보고서에서 다시 돌리지는 않음

#### C7. 공개 화면에 빈칸·전화번호가 없다(KR2) — ✅

- **입력:** 사이트맵의 37개 페이지 전체
- **기대값:** 빈칸 표시·전화번호 0건
- **결과값:** [사이트] 37개 페이지에서 0건

#### C8. 점검 목록이 글을 고칠 때 바로 갱신된다(`AFR-06` "글을 고칠 때마다 다시 점검") — ❌

- **입력:** 전화번호가 든 글에서 점검 탭을 연 뒤, 본문에서 전화번호를 지움
- **기대값:** 목록의 "해결 필요"가 바로 사라진다
- **결과값:** [로컬] 본문을 고친 뒤 3초가 지나도, 제목을 고쳐도 "해결 필요 1"이 그대로. 다른 버튼을 눌러 화면이 다시 그려질 때까지 옛 상태. (발행 버튼을 누를 때는 다시 계산해서 번호를 지운 글은 저장됨)

#### C9. 서버(보안 규칙)도 빈칸·전화번호 든 공개 글을 거부한다 — ➖

- **입력:** 화면을 우회해서 저장
- **기대값:** 거부된다
- **결과값:** 규칙 파일에 같은 패턴(`publishable()`)이 있는 것만 확인. 화면을 우회한 실제 저장 시도는 관리자 권한이 필요해 하지 못함

### D. 작성 부담 (`AFP1`, `AFR-01`~`05`)

- **결과값:** 실제로 300회를 쓰지 않아 못 함(가짜 환경과 코드로만 확인)

## 4. 발견한 문제

**1. 관련 없는 글도 추천 카드로 연결됨(B7). 한국어의 흔한 조각("입니", "니다")만 겹쳐도 기준을 넘음**

- **영향:** 글이 몇 편 안 될 때 엉뚱한 글이 "이어서 읽을 글"로 나옴
- **상태:** 고침·배포함(`build.js`, 흔한 조각을 덜 세고 기준을 0.055로). 사이트에서 카드 수와 추천 내용(B8)을 다시 확인함. 글 4편 중 3편은 주제가 이어지고, 「모바일 관리자 화면」만 약함

**2. 점검 목록이 글을 고칠 때 바로 갱신되지 않음(C8). 본문 입력은 초안만 저장하고 점검 목록을 다시 그리지 않음**

- **영향:** 전화번호를 지워도 "해결 필요"가 남아 보임. 발행할 때는 다시 계산해서 저장은 됨(안전 문제는 아님)
- **상태:** 수정 안 함

**3. 1차 개선의 이벤트(`post_read` 등)가 코드에 없었음(F4)**

- **영향:** 요약 효과를 읽기율로 비교하는 지표(`AFP3-H1`)를 잴 수 없었음
- **상태:** 구현·배포함(읽기 진행도, 완독, 댓글, 공유, 첨부). 이벤트가 GA에 실제로 쌓이는지는 며칠 뒤 확인해야 함. 좋아요·스크랩·검색·로그인 이벤트는 아직 없음

## 5. 확인하지 못한 것

- **F4 새 읽기·공유·댓글·첨부 이벤트가 GA에 도착하는지, 링크 복사 성공과 댓글 이벤트** — 운영자 브라우저는 GA가 꺼져 있고, 시험하는 패널이 숨겨져 클립보드가 막힘. 댓글은 실제 저장이 필요해 하지 않음. 방문자 브라우저에서 이벤트가 쌓인 뒤 GA 실시간·이벤트 화면으로 확인
- **C9 서버 규칙이 빈칸·전화번호 든 글을 거부하는지** — 화면을 우회해 저장하려면 관리자 권한이 필요하고, 실제 데이터에 잘못된 글이 저장될 위험이 있어 하지 않음
- **E10 실제 서버의 한도 초과 동작** — 실제로 300회를 쓰지 않음
- **F3 GA 보고서·탐색에서 맞춤 측정기준 값으로 나눠 보이는지** — 등록한 날이라 처리 시간이 필요. 하루쯤 뒤 확인
- **G3 화면 낭독 프로그램, 사파리·엣지** — 환경이 없음
- **KR3 AI 제안 적용률의 기준값** — 사용 기간이 짧아 측정 4주 뒤에 확인(2026-12-23 예정)
- **글을 올린 뒤 시간이 지나야 보이는 것** — 월간 점검(첫 확인 2026-12-02), 방문자 지표

## 6. 시험의 한계와 부작용

- **샘플은 제가 만든 뚜렷한 예**입니다. 영문 이름·약어·키워드 없는 내부 자료 같은 애매한 경우의 AI 점검 정확도는 모릅니다(C6의 표본 20건도 같은 한계).
- 로컬 시험 환경은 가짜 저장소와 가짜 AI를 씁니다. 화면과 흐름은 확인되지만, 실제 AI의 품질이나 실제 저장은 아닙니다.
- **부작용:** 실제 AI 호출 4회(이번 달 한도의 약 1%), 시험용 익명 로그인 계정 1개(시험 뒤 삭제), 관리자 제외 표시를 GA 시험 동안 잠시 껐다가 되돌림, AI 이용 기록에 점검 실행·찾은 건수가 쌓임. **실제 사이트에 저장된 글은 없습니다.**
- 같은 날 앞서 한 시험(C6, F2, F3)은 결과를 가져다 썼고 이번에 다시 돌리지 않았습니다.

## 7. 종합 판단

1. **기획 의도는 대부분 지켜집니다.** 글을 쓰고 공개하고 읽히는 흐름에서 AI는 제안만 하고, 사람이 승인하며, 방문자 화면은 AI를 부르지 않고, 관리자가 아니면 접근이 막힌다는 세 원칙이 실제로 확인됐습니다(E1·E2·D1·C2).
2. **지표는 2개가 목표에 못 미칩니다.** KR1 한 줄 요약 채움률 93.5%(기존 글 2편이 비어 있음), KR3는 측정 기준이 없음. KR2(0건)와 KR4(0회)는 달성입니다.
3. **독자 쪽(`AFP3`)이 가장 약합니다.** 요약 승인 구조는 정확하지만, 추천이 관련 없는 글을 걸러내지 못하던 문제(B7)는 고쳐서 배포했지만, 읽기율을 잴 이벤트는 구현해 배포했습니다(F4). 다만 이벤트가 GA에 실제로 쌓이는지는 아직 못 봤고, 독자에게 도움이 되는지는 아직 증명되지 않았습니다.
4. 안전 쪽은 의도대로입니다. 문제는 화면 표시가 늦게 갱신되는 것(C8) 하나입니다.
